# MeshKit 오픈소스 런칭 계획

작성일: 2026-08-24
목표 시점: 2026년 9월 초 (서울과기대 수업 개강에 맞춰 공개 — 첫 외부 사용자가 곧 수강생)

## 한 문단 요약

MeshKit을 오픈소스로 공개하되, 그냥 코드를 여는 게 아니라 **누가 포크해도
빼앗아갈 수 없는 세 가지**를 먼저 만들어놓고 연다. ① "MeshKit 호환"이
무엇인지 판정하는 시험지(컨포먼스 스위트), ② 누구나 읽고 구현할 수 있는
스펙 문서, ③ MCP 표준 커뮤니티 안의 공식 확장 자리. 코드는 복제될 수
있지만 이 셋은 복제가 안 된다. 이걸 4개의 작업 묶음(WS1~WS4)으로 나눠서
진행한다.

## 왜 이 순서인가

우리가 팔려는 건 앱이 아니라 **프로토콜**(에이전트가 다른 앱을 안전하게
호출하는 규약)이다. 프로토콜은 남들이 따라 만들어줘야 이기는 게임이고,
남들이 따라 만들게 하려면 "어떻게 만드는지"(스펙)와 "제대로 만들었는지"
(시험지)를 우리가 쥐고 있어야 한다. 그래서 코드 공개보다 시험지와 스펙이
먼저다.

---

## WS1. 시험지 만들기 — `meshkit-conformance`

### 이게 뭔가

지금 우리 저장소에는 이미 "정답지"가 있다.
`meshkit-android/vectors/wire-compat.v1.json` — Swift SDK로 실제 서명해서
뽑아낸 요청·영수증 샘플 모음이다. Swift, Kotlin, Python 세 구현이 전부
이 파일 하나로 서로 검증한다. 새로운 언어로 MeshKit을 구현한 사람이
"내 구현이 맞나?"를 확인하려면 이 파일만 통과하면 된다.

이걸 테스트 파일 취급에서 **"MeshKit 호환의 공식 정의"로 승격**시키는 게
WS1이다. 쿠버네티스가 인증 프로그램으로 짝퉁 파편화를 막은 것과 같은 수다.
대기업이 우리 코드를 포크해도, "MeshKit 호환" 도장은 우리 시험지를
통과해야만 받을 수 있다.

### 실제로 할 일

1. 저장소 안에 `meshkit-conformance/` 디렉토리를 새로 만들고 아래를 옮긴다:
   - `vectors/wire-compat.v1.json` (정답지 — 지금 위치에서 이동)
   - `generators/swift/` (정답지를 만드는 Swift 프로그램 —
     지금의 `scripts/wire_vectors_gen/`)
2. `COMPATIBILITY.md`를 새로 쓴다. "호환"을 3단계로 정의한다:
   - **1단계 (전선 호환)**: 정답지의 문자열·해시·서명 입력을 한 바이트도
     다르지 않게 재현하고, 정답지의 서명을 검증할 수 있다.
     (주의: 서명 바이트 자체를 비교하면 안 된다 — 애플 CryptoKit은 같은
     입력에도 매번 다른 서명을 내놓기 때문. "서로의 서명을 검증한다"가
     기준이다.)
   - **2단계 (신뢰 호환)**: 공격을 막아낸다. 변조된 주문, 재사용된 요청
     (리플레이), 예산 초과 결제, 서명 없는 요청, 남을 사칭한 호출자 —
     이걸 전부 정해진 에러 코드로 거절해야 한다. 거절 목록은 이미
     `meshkit-py/tests/test_trust.py`에 코드로 있다. 이걸 사람이 읽는
     체크리스트로 옮긴다.
   - **3단계 (전송 호환)**: 실제 통로(iOS URL 스킴, 안드로이드 인텐트,
     HTTP/MCP) 중 하나에서 "영수증이 없으면 완료가 아니다" 규칙까지
     지킨다.
3. 규칙 하나를 못박는다: **정답지는 버전별로 불변이다.** 통신 형식을
   바꾸려면 새 버전 파일을 만들고, 스펙 버전을 올리고, 세 SDK를 같은
   커밋에서 전부 고쳐야 한다.
4. 공개 시점에 이 디렉토리를 별도 저장소로 분리한다(지금은 모노리포 안에
   그대로 둔다).

**완료 판정:** 우리를 전혀 모르는 사람이 이 저장소 하나만 받아서,
COMPATIBILITY.md를 읽고, 새 언어(예: Go) 구현을 스스로 인증할 수 있으면
끝난 것.

## WS2. 스펙 문서 — 코드 없이도 구현 가능하게

### 이게 뭔가

지금 프로토콜의 진짜 내용은 `docs/agentos-trust-layer.md`와 코드 주석에
흩어져 있고, 전부 "우리 Swift 코드가 이렇게 한다" 식으로 쓰여 있다.
외부인이 따라 구현하려면 우리 코드를 읽어야 한다 — 이건 스펙이 아니다.
표준 문서처럼 "구현과 무관하게, 이렇게 동작해야 한다(MUST)"로 다시 쓴다.

### 실제로 할 일

`spec/` 디렉토리에 문서 6개. 쓰는 순서 = 아래 순서 (뒤 문서가 앞 문서를
쌓아 올리는 구조):

| 문서 | 내용 (한 줄) |
|---|---|
| `meshkit-canonical-v1.md` | 데이터를 해시하기 전에 한 줄로 펴는 규칙 (정렬, 이스케이프, 논스 결합) |
| `meshkit-request-v1.md` | 요청 봉투: 어떤 12개 필드를 어떤 순서로 서명하는가 |
| `meshkit-receipt-v1.md` | 영수증: 왜 실행한 앱(타겟)만 서명할 수 있고, 요청과 어떻게 짝을 맞추는가 |
| `meshkit-trust-v1.md` | 검증 순서(어느 하나라도 실패하면 즉시 거절), 위험 등급, 동의 등급, 예산 규칙, 에러 코드 |
| `meshkit-registry-v1.md` | 앱 등록 명세(OCG 매니페스트): 능력 선언, 공개키, 서명 |
| `bindings/` 3개 | 각 통로별 규칙: iOS URL 스킴 / 안드로이드 인텐트 / MCP(2026-07-28) |

작성 규칙 (품질 기준):

- 표준 문서 어휘(MUST/SHOULD/MAY)를 쓴다. Swift니 Kotlin이니 하는 언어
  이름은 등장하지 않는다.
- **검증 가능한 문장마다 근거를 단다**: "이 MUST는 정답지의 이 필드로
  확인된다" 또는 "2단계 거절 목록의 이 케이스로 확인된다". 확인할 방법이
  없는 MUST는 쓰지 않는다.
- 무에서 창작하는 게 아니다 — 기존 문서 3개와 SDK 3개에서 **추출**하는
  작업이다.

**완료 판정:** `spec/` + 정답지만 주고 (우리 코드는 안 보여주고) 새 구현을
만들 수 있으면 끝난 것.

## WS3. 기여 규칙과 운영 원칙 — 저장소 루트의 문서 4개

### 이게 뭔가

외부 개발자는 코드보다 이 문서들을 먼저 읽는다. "이 프로젝트에 기여해도
되나? 운영자가 갑자기 규칙을 바꾸진 않나?"에 대한 답이다. 분량은 작지만
신뢰를 결정한다.

### 실제로 할 일

1. **CONTRIBUTING.md** — 세 SDK 각각의 개발 환경 설정과 테스트 명령. 그리고
   이 프로젝트의 헌법 한 줄: *"통신 형식을 건드리는 변경은 정답지 재생성 +
   세 SDK 동시 수정이 한 커밋에 있어야 하며, 상호 검증을 깨는 PR은 CI가
   자동으로 거부한다."* 기여자 서명은 DCO(커밋에 서명 한 줄)만 요구.
   CLA(별도 계약서)는 안 받는다 — 학생 기여의 진입 장벽이 되기 때문.
2. **GOVERNANCE.md** (한 페이지) — 역할 세 개: 메인테이너(머지 권한),
   스펙 에디터(규범 문서 수정 권한 — 초기엔 창립자), 기여자. 결정 방식:
   코드는 "반대 없으면 진행", 스펙 변경은 공개 이슈 + 2주 의견 수렴 +
   에디터 승인. 그리고 한 문장 명시: "채택이 충분해지면 중립 재단(Agentic
   AI Foundation)으로 거버넌스를 이관할 의사가 있다." — 이 문장을 미리
   써두는 것 자체가 신뢰 신호다.
3. **SECURITY.md** — 취약점을 발견하면 어디로 비공개 제보하는지, 90일
   협조 공개 원칙, 범위(서명 위조·검증 우회·리플레이·예산 우회는 범위 안,
   데모 앱은 최선 노력).
4. **CODE_OF_CONDUCT.md** — Contributor Covenant 2.1 표준본 그대로.

추가로 두 가지:

- **README.md 전면 재작성** — 지금 README는 iOS 데모 설명서다. 새 README는
  이야기부터 시작한다: "애플과 구글은 앱 능력 목록을 만들고 그걸 호출할
  권리를 자기네 Siri/Gemini에만 줬다. MeshKit은 인가된 어떤 에이전트든
  검증 가능한 동의와 영수증으로 앱을 호출하는 열린 대안이다." 그 다음
  3개 SDK + 시험지 증명, 그 다음 5분 퀵스타트(meshkit-py).
- **CI 설정 (GitHub Actions)** — 모든 PR에서 Swift·Kotlin·Python 테스트 +
  상호 검증 스크립트 2개를 자동 실행. 헌법을 사람이 아니라 기계가
  집행하게 만든다.

**완료 판정:** 외부인이 클론부터 상호 검증 통과까지 아무에게도 안 물어보고
도달할 수 있고, 형식을 깨는 PR이 CI에서 친절한 에러 메시지와 함께
떨어지면 끝난 것.

## WS4. MCP 공식 확장 제안 — `ai.meshkit/trust`

### 이게 뭔가

MCP는 에이전트가 도구를 호출하는 사실상의 표준이고, 2026년 7월 개정판부터
"확장"을 공식 제도로 만들었다(누구나 자기 도메인 이름으로 확장을 정의해
등록 제안 가능). 우리는 이미 MeshKit을 `ai.meshkit/trust`라는 MCP 확장으로
구현해놨다 — 도구 호출에 서명·동의·영수증을 얹는 확장. MCP 본체에는 이
기능이 없고, 이 빈자리에 **가장 먼저 신뢰성 있는 제안을 꽂는 쪽이 그
카테고리의 표준이 된다.**

### 실제로 할 일

1. 제안서를 쓴다 (WS2의 `bindings/mcp-2026-07-28.md`가 제안서 본문을 겸함):
   - **왜 필요한가** — 결제나 사용자 데이터 수정처럼 되돌릴 수 없는 도구
     호출에는 "누가 시켰는지"(서명), "얼마까지 허락했는지"(예산 동의),
     "정말 실행됐는지"(영수증)의 증명이 필요한데 MCP 본체에는 없다.
   - **어떻게 동작하는가** — 이미 구현된 그대로: 서명 봉투는 요청
     메타데이터에, 영수증은 응답 메타데이터에, 봉투 내용과 도구 인자는
     반드시 일치.
   - **기존 표준과의 관계** — 구글 AP2(결제 사전 승인 증명)와는 경쟁이
     아니라 상호 보완: "AP2로 승인받고, MeshKit으로 실행을 증명한다."
   - **증거** — 구현 3개 + 시험지 + 실제 수업에서 십수 팀이 쓰고 있다는
     사용 데이터.
2. 제출 채널: MCP 공식 저장소의 제안 절차(SEP). 제출 시점에 절차가 바뀌었을
   수 있으니 그때 다시 확인.
3. **제출 시점이 핵심이다: WS1·WS2가 공개된 다음, 첫 수업 코호트 데이터가
   생긴 다음.** 살아있는 시험지와 3개 구현을 링크한 제안은 "표준"으로
   읽히고, 비공개 저장소를 링크한 제안은 "홍보"로 읽힌다. 현실적으로
   9월 말~10월.

**완료 판정:** 제안이 MCP 커뮤니티에 공개 게시되고, 스펙·시험지·구현 3개가
링크로 연결되어 있으면 끝난 것.

## 전체 일정

```text
지금 바로        WS1 (디렉토리 정리 + COMPATIBILITY.md)
                 WS3 (문서 4개 + README + CI)
                 → 둘 다 기계적인 작업, 서로 독립적, 먼저 해치운다

공개 전          WS2 (스펙 6개 추출 — 가장 큰 글쓰기 작업)

9월 초 공개      저장소 공개 + 시험지 저장소 분리
                 "열린 호출자" 내러티브로 발표
                 수업 9~10주차 과제가 공개 저장소를 가리키게 연결

10월             WS4 제출 (첫 코호트 사용 데이터를 들고)
```

## 공개 전 최종 점검표

- [ ] `meshkit-conformance/` 정리 완료, 상호 검증 스크립트 2개가 CI에서 통과
- [ ] COMPATIBILITY.md — 3단계 정의 + 거절 체크리스트
- [ ] `spec/` 문서 6개 — 모든 MUST에 확인 방법이 달려 있음
- [ ] CONTRIBUTING / GOVERNANCE / SECURITY / CODE_OF_CONDUCT 루트에 존재
- [ ] README가 데모 설명서가 아니라 프로토콜을 팔고 있음
- [ ] CI: SDK 테스트 3벌 + 상호 검증 2벌
- [ ] **저장소 히스토리 감사** — 키·토큰·학생 데이터가 커밋 이력에 없는지
      (테스트의 데모 시드는 데모 전용으로 문서화돼 있으면 괜찮음)
- [ ] 발표문 초안 — "앱투앱 온디바이스 에이전트 결제 표준은 아직 없다"는
      공백 + 시험지 증명 + 수업 연계
- [ ] WS4 제안서 초안 완성 (제출은 공개 + 코호트 데이터 이후)

## 이 계획에서 하지 않는 것

- **수익화 설계** (호스팅 레지스트리, 인증 서비스, 게이트웨이) — 나중에.
  프로토콜의 개방성을 해치는 방식은 그때도 하지 않는다.
- **재단 기부** — 첫 코호트가 끝나고 실사용 근거가 생기면 그때 검토한다.
